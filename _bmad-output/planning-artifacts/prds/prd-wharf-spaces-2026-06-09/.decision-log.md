## Session 1 — 2026-06-09 / 2026-06-10

### DL-001 — Single app binary
**Decision:** One app on the App Store; tenant branding and config loaded at runtime. No per-tenant builds.
**Rationale:** Simpler release process; AND Digital maintains one binary.

### DL-002 — Platform operator model
**Decision:** AND Digital is the platform operator — approves new tenants and controls email domain allowlists via the onboarding form web app, not Firebase console.
**Rationale:** Self-serve philosophy; minimise AND Digital's ongoing manual maintenance burden.

### DL-003 — V1 deadline
**Decision:** End of August 2026 (2026-08-31).
**Team:** 5 developers + 2 product people, mixed disciplines.

### DL-004 — User roles (v1)
**Decision:** Four roles — End User (mobile), Company Admin (mobile), AND Digital / Platform Operator (web), Building Admin (web only).
**Note:** Building Admin mobile access is explicitly out of scope for v1.

### DL-005 — Auth strategy
**Decision:** Per-tenant config supporting Google, Microsoft, Apple (iOS), and email/password. AND Digital controls which email domains are allowed per tenant (not the Company Admin). Replaces current hardcoded @and.digital Google-only config.

### DL-006 — Scope boundary
**Decision:** In-scope v1: mobile app (iOS + Android), React web app (two screens), multi-tenancy, feature parity, GDPR/security/observability.
**Out of scope v1:** User-facing web booking portal, billing, floor maps, recurring bookings, calendar integration, hardware integration, dedicated company admin web interface.

### DL-007 — Design approach
**Decision:** New mobile app matches existing screens as closely as possible. Screenshots in /docs/screenshots/. Some new screens need design (login, events modal, guest booking, waitlist state, etc.). Tenant-specific strings become configurable; layouts and interaction patterns carry over.

### DL-008 — NFR concerns to address
**Decision:** Five NFR sections required in the PRD: GDPR / privacy / data governance, Security, Observability / logging, Support model (not yet decided — needs discussion), Performance / reliability.

### DL-009 — Working mode
**Decision:** Coaching path, Vision + Features entry point.
**Feature group order agreed (14 groups):**
Mobile: (1) Auth & onboarding, (2) Desk booking, (3) Parking booking, (4) Events & notes, (5) Who's in list, (6) Push notifications, (7) Company admin mobile capabilities.
Web: (8) Tenant onboarding form, (9) Parking occupancy view.
Platform/cross-cutting: (10) Multi-tenancy & white-label theming, (11) GDPR/privacy, (12) Security, (13) Observability & logging, (14) Support model.

## Session 2 — 2026-06-11

### DL-010 — Auth access model
**Decision:** Individual allowlist model (not domain-level). Company Admin registers each user by email address. Anyone not on the allowlist sees "please contact your company administrator" and cannot proceed.

### DL-011 — Demo/reviewer login purpose
**Decision:** Demo login mode exists to satisfy App Store review requirements (Apple reviewers need a way in without a real tenant account). Not a general demo product feature.

### DL-012 — First sign-in experience
**Decision:** No onboarding steps after sign-in — user lands directly on the booking screen. Push notification permission prompt shown on first sign-in.

### DL-013 — Email/password verification method
**Status:** Deferred. OTP or email link — to be confirmed before architecture. Logged as OQ-001.

### DL-014 — Desk booking: feature parity confirmed
**Decision:** Desk booking in the rebuild matches the current app (week calendar, AM/PM/All Day slots, per-tenant capacity, waitlist, guest booking, cancellation). No new behaviours added to v1.

### DL-015 — Tenant-configurable strings on booking screen
**Decision:** "Events in the clubhouse" → tenant-configurable string (generic default: "Events in the office"). "ANDis" count label in Who's In → also tenant-configurable. Full treatment in feature groups 4 (Events & Notes) and 10 (Multi-tenancy).

### DL-016 — Parking booking window rules: tenant-configurable
**Decision:** The booking window rules (how far ahead, time-of-day cutoffs, capacity pooling) are tenant-configurable, not AND Digital-specific hardcoded logic. Platform enforces rules using server time (anti-manipulation).

### DL-017 — Parking capacity model: per-tenant groups
**Decision:** Each tenant defines their own internal groups with their own parking allocations. Replaces the hardcoded BusinessUnit enum (murray/tenzing/adams/unknown).

### DL-018 — Events/notes: any user can author
**Decision:** Any signed-in user (not just admins) can create/edit the shared daily note for their tenant. Simplifies role-based access for this feature.

### DL-019 — isOfficeClosed deferred to v2
**Decision:** The `isOfficeClosed` field (formerly `isClubhouseClosed`) is not surfaced in the v1 UI. Data model preserves the field for a future version.

### DL-020 — Events banner label: tenant-configurable
**Decision:** "Events in the clubhouse" → tenant-configurable string. Default: "Events in the office".

### DL-021 — Who's In: fixed section headers
**Decision:** "Who's in?" and "Who's parking?" remain as fixed strings — not tenant-configurable. Member count term ("ANDis") is tenant-configurable.

### DL-022 — Company Admin mobile capabilities: guest parking only
**Decision:** Company Admins have no dedicated mobile admin UI in v1. Their only elevated mobile permission is guest parking (FR-019). All tenant configuration is done via the web platform.

### DL-023 — Allowlist management is on the web platform
**Decision:** Company Admins add users to the allowlist via the web platform, not the mobile app. Revises earlier assumption in DL-010 which left the surface unspecified.

### DL-024 — Tenant onboarding form captures: domain, auth provider, first admin
**Decision:** The AND Digital onboarding form provisions: domain name, auth provider config, first Company Admin email. Further configuration (capacity, groups, branding) done by Company Admin post-onboarding.

### DL-025 — Allowlist management on web platform (Company Admin)
**Decision:** Company Admins add/remove individual user emails from their tenant's allowlist via the web platform.

### DL-026 — Tenant suspension: lock out immediately, data preserved, reversible
**Decision:** Suspending a tenant immediately locks out all users. Data persists. Reinstatement restores full access without data loss.

### DL-027 — Permanent tenant removal: capability exists, usage discretionary
**Decision:** Hard delete functionality built in v1. Whether AND Digital uses it immediately is their call. Data retention/GDPR obligations on deletion logged as OQ-002.

### DL-028 — Building Admin parking occupancy view: out of scope v1
**Decision:** Feature group 9 (Building Admin parking occupancy view) removed from v1 scope. Scope section and web app description updated accordingly.

### DL-029 — Branding configured by Company Admin, not AND Digital
**Decision:** Tenant branding (colours, logo) configured by Company Admin via the web platform. AND Digital does not set branding during onboarding.

### DL-030 — App name: TBD
**Decision:** App name will change from the current AND Digital-specific name. New name not yet decided. Logged as OQ-003.

### DL-031 — User removal triggers data deletion
**Decision:** Removing a user from the allowlist must delete their personal data and booking history. Not required to be instant but must be part of the removal process.

### DL-032 — Right to erasure: manual handling in v1
**Decision:** No in-app erasure flow in v1. Requests handled manually by AND Digital or Company Admin out of band.

### DL-033 — Tenant isolation is a server-side security requirement
**Decision:** Tenant isolation must be enforced at the API/backend layer, not just the data model or UI. A user in Tenant A cannot access Tenant B's data regardless of client behaviour.

### DL-034 — Observability: tenant-attributed, user consent toggle retained
**Decision:** All crash and analytics events attributed to tenant. Analytics/Crashlytics consent toggle carries forward from current app (login screen).

### DL-035 — Support model v1: direct contact to AND Digital
**Decision:** Company Admins contact AND Digital directly for support. No in-app or ticketing mechanism in v1. Formal support model deferred to a future phase.
